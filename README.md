# lodestonemaps.com

Site for Lodestone Maps: a home page, two product pages and two legal pages.
React + Vite + TypeScript, plain CSS, prerendered to static HTML, no server.

```
npm install
npm run dev        # http://localhost:5173
npm run build      # typecheck, client build, SSR build, prerender -> dist/
npm run preview    # serve dist/ locally
npm run check      # acceptance checks against dist/index.html
```

`npm run check` also accepts a URL, so it can be run against the live site
after a deploy: `npm run check -- https://lodestonemaps.com/`

## Content

All copy lives in `src/site-data.ts`. Nothing else needs editing to change
wording. Pages (`pages` in site-data): `/`, `/bim-buyers-map`,
`/construction-market-map`, `/privacy`, `/terms`. Home page order and anchors:

`Hero` -> `Maps` #maps -> `What is in a row` #row -> `Built to order`
#built-to-order -> `How an order works` #how-an-order-works -> `Position`
#position -> `Sources` #sources -> `Standard` #standard -> `Who is Lodestone`
#about -> `FAQ` #faq -> `Contact` #contact

A product page links to the form as `/?map=<value>#contact`; the form reads the
`map` parameter and selects that map.

`#method` and `#coverage` are kept as aliases resolving to `#sources` and
`#maps`, so links sent before the rewrite still land in the right place. They
are zero-height spans rendered immediately before their target section, so they
work without JavaScript.

### Voice rules enforced by `npm run check`

- No em dashes and no en dashes anywhere in the output, including HTML
  attributes. Hyphens are fine.
- Lodestone in the third person. No "we" (Privacy and Terms excepted: legal
  pages speak as "we").
- No exclamation marks.

### Numbers are floors, not measurements

`figures` in `src/site-data.ts` holds `20,000+` companies and `70+` sources.
Both are floors, re-checked against the live dataset before each publish; the
page changes only if the real count falls below the floor. Do not edit them to
a precise number.

## Prerendering

The build renders the app to static HTML so the copy and the FAQ are in the
served document rather than behind JavaScript:

1. `vite build` produces the client bundle and a `dist/index.html` whose body is
   an empty `#root`. That file is the template for every page.
2. `vite build --ssr src/entry-server.tsx` produces `dist-ssr/entry-server.js`.
3. `prerender.mjs`, for each page in `pages`: replaces the block between
   `<!--head:start-->` and `<!--head:end-->` with that page's head (title,
   description, canonical, social cards, JSON-LD), renders the page into `#root`
   with `data-page`, and writes `dist/<file>` (`index.html`, `bim-buyers-map.html`,
   ...). Cloudflare Pages serves `bim-buyers-map.html` at `/bim-buyers-map`.
   Then it writes `sitemap.xml` with every page and deletes `dist-ssr`.

`src/main.tsx` reads the page from `data-page` (or from the path in `npm run
dev`), calls `hydrateRoot` when `#root` already has children and `createRoot`
when it does not.

## SEO assets

The head of each page (title, description, canonical, OpenGraph, Twitter and
JSON-LD) is generated by `head()` in `src/entry-server.tsx` from
`src/site-data.ts`. The home page carries Organization, two Product blocks and
FAQPage; product pages carry Organization and their Product; legal pages carry
Organization. The FAQPage is built from the FAQ copy, so it never drifts.

`dist/sitemap.xml` is generated by `prerender.mjs`, not committed, so its
`lastmod` tracks the date of the last commit (falling back to the build date if
git is unavailable in the build image).

`public/og.png` (1200x630) is generated from the live hero. The icons
(`favicon.ico`, `favicon-48.png`, `favicon-96.png`, `icon-192.png`,
`apple-touch-icon.png`, `icon-512.png`, the Organization logo in JSON-LD) are
rendered from `favicon.svg` (2026-10-03; the earlier apple-touch-icon was a
capture of a broken image). `google87ca82c337dd98f9.html` verifies the site in
Google Search Console: do not remove it. They are
committed, so a normal build does not need a browser. Regenerate them only when
the hero changes.

## Web3Forms

The contact form POSTs straight from the browser to `api.web3forms.com`, which
is what keeps the site fully static. Set `VITE_WEB3FORMS_KEY` in `.env` locally
and in the Cloudflare project's environment variables; Vite inlines it at build
time, so it must be present before the build runs.

The key is public by design. Spam is handled by the hidden `botcheck` honeypot
in `src/components/Contact.tsx`, not by keeping the key secret.

## Deploying to Cloudflare

Turn **Scrape Shield -> Email Address Obfuscation off** for this zone. With it
on, Cloudflare rewrites the contact address into `[email protected]` plus a
decoder script in the served HTML, which defeats printing the address as plain
text for crawlers. It applies to the custom domain, not to `*.pages.dev`, so the
two can look different.

Pages, connected to the git repo:

- Build command: `npm run build`
- Build output directory: `dist`
- Environment variable: `VITE_WEB3FORMS_KEY`

Both build fields must be set. With an empty build command, Pages skips the
build, reports success, and publishes the repository root, which serves the
unbuilt `index.html` and fails with a MIME type error on `/src/main.tsx`.

`public/_headers` sets security headers and a one-year immutable cache on
`/assets/*` and `/fonts/*`. It is copied into `dist/` and read by Pages
automatically. There is no router and no server function, so no SPA fallback is
needed.

## Design system

Colour, type, spacing and frame tokens are in `src/styles/tokens.css`, copied
from `brandbook_v2.pdf` pages 13 and 14. The brandbook and the hero reference
image are not committed; page references here are provenance for the values, not
links to files in this repo.

Fonts are self-hosted in `public/fonts/` (latin and latin-ext subsets of Spectral
300/400/600, Libre Franklin 400/500, IBM Plex Mono 400, 240 KB total). The
brandbook specifies Google Fonts; self-hosting removes the third-party request.

### Two deliberate divergences from the brandbook

**1. `--rail` is renamed to `--rail-w`.** The brandbook defines `--rail` twice:
as a colour (`#333A3E`, p.13) and as a width (`168px`, p.14). Pasting both
blocks as instructed silently overwrites the colour with the width. The colour
keeps the original name; the width is `--rail-w`.

**2. The hero.** It follows the supplied reference image, not brandbook pattern
A. It fills the viewport (`100svh`), drops the side rail, and puts a wine wash
with compass rings behind the type. This contradicts three stated rules: "no
gradients", "no wine on large surfaces", and "one wine band per screen". The
wash peaks at roughly `#581919` over the asphalt ground, so it never gets
brighter than the brand wine `#5F1616`. The brandbook's wine stat band is not
used, so the hero is the only wine surface on the page.

`--rule-dark` and `--rail-w` are therefore unreferenced. They are kept because
`tokens.css` mirrors the brandbook rather than only what the site uses today.

Everything else follows the brandbook: square corners throughout
(`border-radius: var(--radius)`, which is `0`, on every element), structure
drawn with 1px rules rather than filled cards, and no drop shadows.

Breakpoints, per brandbook p.14: at 900px the layout goes single-column; at
640px display type drops to 40px and page padding to 24px. The hero's compass
rings are floored with `top: max(17%, 140px)` so they cannot ride up into the
navigation on a short viewport.

### Navigation

With five sections plus the phone and WhatsApp links the inline navigation
needs about 1,000px at 13px, so below 1301px it collapses into a menu: a hairline button in the
header and a full-screen asphalt panel with the items set in Spectral. The panel
closes on Escape, on selecting an item, and on pressing the button again, and it
locks body scroll while open. If a nav item is added or renamed, re-measure and
raise the 1300px breakpoint in `app.css` to match, or the row will wrap again.
